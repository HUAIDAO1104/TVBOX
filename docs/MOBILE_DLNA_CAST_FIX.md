# 手机 DLNA 投屏修复

基线：`3a2e16c3ba8b6895f95e1d1059a9ad4611e24c83`（v5.5.86）。

## 问题与原因

反馈：创维电视自带接收端和乐播都能被发现，但大多数视频只出现很小的流量，随后播放失败；手机本地播放正常。

代码审查确认，旧实现把原始视频 URL 直接交给电视，并把请求头 JSON 放进 DIDL `dc:description`。这是应用之间的私有约定，普通 DLNA 接收端不会据此设置 Referer、User-Agent、Cookie 或 Authorization。另一个问题是把手机的 `127.0.0.1` 简单替换为局域网 IP；只监听回环地址的插件代理仍然不能被电视访问。

这些缺陷可以解释上述症状，但本次没有连接用户的创维电视或取得其播放日志，不能把代码验证等同于真机验证。

## 修改

- 电视获得手机局域网中的临时媒体地址，由手机使用播放器的 OkHttp 网络配置和请求头读取实际视频。
- 保留手机回环 URL，由转发器在手机上访问；不把上游凭据放入投屏元数据或链接。
- 改写 HLS 主列表、子列表、音轨、字幕、分片、密钥及初始化片段地址；相对路径按重定向后的实际地址解析，保留签名查询参数。
- 视频保持流式传输；仅播放列表允许有限缓冲，上限 2 MiB。并发分片请求使用独立调用调度器，手机播放器停止请求不会取消电视取流。
- 保留 HTTP Range、206、Content-Range 和 HEAD 语义。未知文件长度不会被误报为零；兼容不正确返回 HEAD 正文的旧式插件服务器。
- 修正播放器网络层 deflate 解压后的响应头与缓冲区复用，避免电视再次解压已解压的数据，以及媒体类型探测消耗后续视频数据。
- 电视真正开始读取媒体字节后才停止手机播放；连接失败、取消和超时会释放对应转发会话。
- 使用 connectedDevice 前台服务及电源/Wi-Fi 锁维持后台传输；通知提供停止操作，连续 30 分钟没有媒体请求时自动清理。
- 会话使用随机标识，资源只能来自当前视频及其播放列表中的已登记地址，不接受任意目标 URL 参数。切换会话会取消旧请求。

## 回归测试

`CastMediaRelayTest` 使用实际 HTTP 套接字和 NanoHTTPD 源服务器，覆盖：

1. 防盗链/鉴权源直接访问失败，而使用手机请求头转发后成功。
2. 请求头快照、重定向、多层 HLS、音轨、字幕、密钥、初始化片段及签名参数。
3. MP4 Range/206/If-Range，已知与未知长度 HEAD，以及不支持 HEAD 的源。
4. 播放列表探测 Range、改写后的 HEAD 长度及后续连接复用。
5. 不等待整段视频下载完成即可读取首批数据，未知长度分块流完整传输。
6. 并发取流、手机请求取消隔离、会话替换、旧会话失效与上游错误。
7. 准备请求和 HEAD 不会被误判为电视播放，超大列表被拒绝，内嵌密钥保持原有语义。

`CastDeflateResponseTest` 通过实际 `ResponseInterceptor` 验证压缩片源在探测、解压和转发后字节保持完整。

标准项目命令：

```sh
./gradlew :app:testMobileArm64_v8aDebugUnitTest --tests 'com.fongmi.android.tv.server.Cast*Test'
```

交付前必须将两个架构的 APK 与 v5.5.86 官方手机版核对：包名相同、签名证书 SHA-256 相同、版本号更高，并完成签名及最终 DEX 兼容检查。密钥仅在原仓库的构建环境中使用，不包含在源码或产物中。测试结果以对应 Actions 运行记录为准。

## 真机验收

在创维自带接收端、乐播分别测试同一条手机可正常播放的 MP4 与 HLS 线路：开始播放、连续播放至少十分钟、拖动进度、手机熄屏及切到后台、切换视频、通知停止传输。确认失败时手机播放不会被提前停止。

本修改不进行视频转码，也不增加电视的编解码器或 DRM 能力；接收端仍需支持片源本身的格式。手机需要与电视保持局域网连通。
